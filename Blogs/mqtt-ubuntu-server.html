Basic Mosquitto broker setup for testing MQTT with an ESP32.

What is MQTT?

MQTT stands for Message Queuing Telemetry Transport. It is a lightweight publish and subscribe messaging protocol often used in IoT systems. It is useful when devices need to send small messages efficiently, especially on low-power devices or unreliable networks.

MQTT uses three main roles: broker, publisher, and subscriber. The broker is the middle server that receives messages and sorts them by topic. A publisher sends data to a topic. A subscriber listens to a topic and receives messages from the broker.

I wanted to test MQTT with an ESP32 microcontroller. My goal was to publish data from the ESP32 like it's status and later control an LED based on messages received from a subscribed MQTT topic. In later versions I may write up on adding a sensor and publishing it's data but for now let's keep it simple.

To do this, I needed an MQTT broker running on my Debian Server. This can be done on most Debian-based systems like Ubuntu that have MQTT packages. The ESP32 would connect to the broker, publish sensor data to one topic, and subscribe to another topic for control messages.

Installing Mosquitto on Ubuntu Server

I used Mosquitto as the MQTT broker. Mosquitto is available from the Ubuntu repositories, so it can be installed using apt. 

sudo apt update
sudo apt install mosquitto mosquitto-clients -y

Then I started the Mosquitto service and enabled it to start automatically:

sudo systemctl start mosquitto
sudo systemctl enable mosquitto
sudo systemctl status mosquitto

Testing publish and subscribe locally

I opened two terminals. In the first terminal, I subscribed to a test topic: 

mosquitto_sub -h localhost -t "test_topic" -v

In the second terminal, I published a test message: 

mosquitto_pub -h localhost -t "test_topic" -m "Testing"

If everything works, the subscriber terminal should show the message.

Allowing other devices on my network to connect

Localhost only tests the broker from the same machine. To connect from another device, like a phone, laptop, or ESP32, the broker needs to listen on the network.

I created a custom Mosquitto config file inside: 

/etc/mosquitto/conf.d/

For testing, I created: 

sudo nano /etc/mosquitto/conf.d/test.conf
You will need your server Ip address on your network, which can be found by running: hostname -I or ip -4 addr.

Then I added: 

listener 1883 >
allow_anonymous true

This opens MQTT port 1883 on the server for testing. Anonymous access is convenient for a testing and setup

After changing the config, I restarted Mosquitto: 

sudo systemctl restart mosquitto
sudo systemctl status mosquitto

Finding the debian Server IP address

To connect from another device, I needed the IP address of the Debian Server: 

hostname -I

or: 

ip -4 addr

For example, if the server IP is 192.168.1.83, then MQTTX, MyMQTT, Node-RED, or an ESP32 can use that address as the broker address.

Testing with MQTTX and Node-RED

After local testing worked, I used MQTTX to create a connection to the broker using the Debian Server IP address. I subscribed to a topic and published test messages to confirm that messages could travel across the network.

Node-RED useful because it lets me build simple flows visually instead of typing every command manually. For example, an MQTT input node can receive sensor data and another node can format it into JSON before sending it to a dashboard, database, or another API.

What I learned

The main idea I learned is that MQTT separates devices from each other. The ESP32 does not need to know every device that wants the data. It only needs to publish to a topic. Any subscriber interested in that topic can receive the data through the broker. I had many issues accessing the MQTT ip, initially this was done on a Debian VM which was configured to block inbound traffic connections, this was resolved by setting it to a bridged network state where the VM connected to the Virtual Box software ip routed to the device NIC.

The next improvement would be adding usernames, passwords, firewall rules, and eventually TLS.
